## 2026-07-28 09:16 - Make warp's repair conditional on actual divergence, and disable git auto-gc in test repos

**Reasoning:** Two defects, both landed on main in the v2.0.0 merge wave. (1) Deleting the derived_docs.mode gate removed TWO conditions that shared one if-statement: whether the repo had adopted the mode (correctly deleted) and whether the branch had actually diverged (should never have been). Losing the second made warp repair every branch, which overwrote the read-only refresh warp performs earlier in the same command -- it printed 'refreshed 2 derived doc(s) from origin/main' and discarded them one statement later. Reproduced against shipped main: a branch forked before main advanced saw only the merge-base content after warp claimed to refresh it. The deeper reason it must be conditional is the SPEC 0.4.1.2 handoff -- a repair surface signals 'this is deliberate' by staging, and a signal asserted on every branch carries no information. (2) Test repos never disabled git's auto-gc, so a background 'git gc --auto' forked by git commit was still writing into .git/objects when t.TempDir cleanup ran, failing RemoveAll with 'directory not empty'. That reddened three PRs on different matrix cells while every test passed locally.

**Alternatives considered:** Have warp skip the refresh when it intends to repair -- rejected: the refresh is the reason the command exists, and a branch that needs repair also needs current context. Compare working-tree content instead of HEAD -- rejected and this one is a trap: the refresh has already written main's tip into the working tree by the time the check runs, so a working-tree comparison sees the refresh itself as divergence and repairs it away, reintroducing the bug. Drop the repair from warp entirely -- rejected: without it, fixing a diverged branch requires --no-verify, and a tool whose repair procedure is 'disable the tool' is a bad tool. Delete the failing TestWarp_DoesNotCommit assertion -- rejected: it was inverted instead, because a clean working tree now means the refresh was discarded, which is exactly the regression worth asserting against.

**Implications:**
- warp on a healthy branch now leaves main's newest derived docs in the working tree, modified and unstaged, and prints no repair clause. A genuinely diverged branch still gets repaired and staged. divergedDerivedDocPaths compares HEAD against the merge-base because it is the committed copy the invariant constrains; DefaultBranchMergeBase's 'HEAD' fallback degrades correctly with no special case, since HEAD against HEAD yields no divergence and therefore no repair. The regression test was mutation-tested -- reinstating the bug makes it fail with the exact expected message. Also corrected a warp.go comment that justified the clobbering as a deliberate trade citing a CTO ruling in PR history; no such ruling exists, the call was mine when I approved the build agent's escalation, and the comment invented provenance for it.
