## 2026-07-28 09:44 - Suppress git's background maintenance in test repos — maintenance.auto, not gc.auto, is the spawn gate

**Reasoning:** My previous fix for the TempDir cleanup race was a confident guess that shipped and did not work. It set gc.auto=0 on the theory that a background 'git gc --auto' was writing into .git/objects during cleanup. That fix was present in the commit that failed again at 13:17, which refutes it directly. The actual mechanism: 'git commit' calls run_auto_maintenance() unconditionally, and its spawn gate is maintenance.auto (default true) -- a SEPARATE key that gc.auto does not influence. Verified with GIT_TRACE2_EVENT on git 2.39.5 rather than reasoned about: with gc.auto=0 alone, git commit spawned 'git maintenance' on 5 of 5 commits; adding maintenance.auto=false took it to 0 of 5; removing it again in the same repo restored 5 of 5. The spawned process can daemonize via maintenance.autoDetach (default true) into a grandchild outside git's process tree, which explains both the load-dependence and why it never reproduces locally -- unloaded it finishes in milliseconds.

**Alternatives considered:** Stop using t.TempDir for git repos and clean up with a tolerant remover that ignores residual files -- rejected for now: it would have worked, but it converts a real signal into a silence, and would equally have masked a genuine leaked-process bug had one existed. Add a package TestMain injecting git config via GIT_CONFIG_COUNT so every helper is covered including future ones -- genuinely better on coverage and worth revisiting, but it changes config resolution for every git subprocess in the package, which is a wider blast radius than this defect justifies. Register a cleanup that polls for quiescence before RemoveAll -- rejected as a timing fix for a timing bug.

**Implications:**
- All four repo-creating helpers now set both keys. Investigated whether logmind itself leaks a subprocess that outlives a command, because that would have been a product bug affecting real users rather than a test annoyance: it does not. Every exec.Command in non-test code pairs with a blocking Run/Output/CombinedOutput, there are zero bare .Start() calls, and the single goroutine in internal/cli only drains stdin. Nothing about this changes what ships in v2.0.0. HONEST GAP: nobody caught the detached maintenance grandchild alive and writing mid-race, so the causal chain to 'directory not empty' is inferred from git's documented detach behavior rather than directly observed. What IS proven is that the mechanism fires and that this config stops it. Verification cannot come from local runs -- the defect only appears under CI load -- so this needs several dozen clean matrix runs before being called fixed.
